## 一、技术选型与架构决策

### 1.1 选型（含理由）

| 项 | 决策 | 理由 / 约束来源 |
|---|---|---|
| 语言 | 原生 JavaScript（ES2022），**不用任何框架** | PRD NF2「零安装」、NF3「单文件」。框架需打包器与 CDN，与离线冲突 |
| 构建 | 自写 `tools/build.mjs` 把 CSS/JS/JSON 内联进单个 HTML | 满足 NF3，且不引入 npm 依赖 |
| 数据 | `data/*.json`（8 个文件），构建时内联为 JS 对象 | 便于单独编辑/校验；300～500 型号约 200～300 KB，可接受 |
| 单测 | Node 内置 `node:test` + `node:assert` | 零依赖，`node --test` 直接跑 |
| 存储 | `localStorage`（键名前缀 `zhuangji:`）+ 手动导出/导入方案 JSON 兜底 | PRD NF6；`file://` 下 localStorage 有丢失风险，故必须有兜底（见风险 R2） |
| .xlsx 导出 | **纯 JS 写入器**（stored 模式 zip + CRC32），不引入 SheetJS | 满足 NF3 单文件；SheetJS 内联约 900 KB，代价过大。降级方案见 R1 |
| 图表/占比条 | 纯 CSS 实现 | 不引入图表库 |
| 字体/图标 | 系统字体 + Emoji/内联 SVG | PRD NF1「无任何外部请求」 |

```
                    ┌─────────────────────────────┐
                    │  data/*.json（8 品类硬件库） │
                    └──────────────┬──────────────┘
                                   │ 构建时内联
                                   ▼
┌──────────────┐        ┌──────────────────────┐
│ CSV 导入(M2) │───────►│  store.js 状态仓库     │
└──────────────┘        │  config / ui / custom │
                        └───────┬──────────────┘
                                │ 任一变更触发
                ┌───────────────┼───────────────┐
                ▼               ▼               ▼
        ┌──────────────┐ ┌────────────┐ ┌────────────┐
        │ rules.js     │ │ power.js   │ │ status.js  │
        │ 32 条规则引擎│ │ 功耗计算   │ │ 状态灯汇总 │
        └──────┬───────┘ └─────┬──────┘ └─────┬──────┘
               └───────────────┼──────────────┘
                               ▼
                    findings[] + power + status
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
```

**关键设计**：`rules.js` / `power.js` / `search.js` / `status.js` 是**纯函数模块，不接触 DOM**，因此可在 Node 中直接单测。所有 DOM 操作集中在 `src/ui/*`。

### 1.3 状态结构（唯一数据源）

```js
store = {
  config: {                 // 已选配置；ID 引用
    cpu: 'cpu-amd-r7-7800x3d' | null,
    motherboard: id | null,
    gpu: id | null,
    memory: id | null,
    psu: id | null,
    cooler: id | null,
    case: id | null,
    storage: [id, ...]      // 可多选，第一个视为系统盘（W11 用）
  },
  ui: {
    category: 'cpu',        // 当前中栏品类
    search: '', filters: {}, sort: {key, dir},
    view: 'table' | 'card',
    compare: [id, ...],     // 勾选对比（2~4）
    rightCollapsed: false
  },
  custom: { cpu: [...], ... },   // CSV 导入的自定义数据
  schemes: { [name]: {config, savedAt} },  // 多方案（M8）
}
```

持久化键：`zhuangji:store:v1`（自动保存，防抖 300ms）。

### 1.4 规则注册表模式（M3 的实现骨架）

每条规则是一个对象，**声明式**描述，便于单测与「规则说明」弹窗复用：

```js
{
  id: 'E1',
  level: 'error',                       // error | warn | info
  title: 'CPU 与主板插槽不匹配',
  categories: ['cpu', 'motherboard'],   // 用于状态灯汇总（PRD 4.4）
  required: ['cpu', 'motherboard'],     // 未选齐则跳过（M3-6），计入 skipped
  fields: ['cpu.socket', 'motherboard.socket'],  // 规则说明弹窗展示
  good: '...', bad: '...',              // 规则说明弹窗的正/误示例
  check(ctx) {
    // ctx = { cpu, motherboard, ... } 已解析为对象（非 ID）
    // 返回 null（通过）或 { reason, advice, refs }
  }
}
```

引擎职责：过滤 `required` → 执行 `check` → 收集 findings → 统计 checked/skipped → 按 level 排序 → 输出给 UI 与状态灯。

2. `node tools/validate-data.mjs` 该品类 **0 错误**

**T1.9 交叉校验的必查项（最容易出错，单独成任务）**
| 检查 | 说明 |
|---|---|
| 插槽字面量统一 | `AM4`/`AM5`/`LGA1700`/`LGA1851`/`LGA1200`/`LGA2011-3`… 与 `enums.js` 完全一致，**不允许** `am4`、`AM4 ` 等变体（否则 E1 误判） |
| 板型字面量统一 | `E-ATX`/`ATX`/`M-ATX`/`Mini-ITX` 与机箱 `formFactors[]` 取值一致 |
| 散热器 socket 覆盖 | 每个 CPU 插槽都有可选散热器（否则 E9 全红） |
| 电源接口覆盖 | 各显卡所需 8pin/12VHPWR 都有电源可满足 |
| 性能分基准统一 | **以 `R7 7800X3D` 游戏分 = 100 为基准**（与 PRD 示例一致），生产力分同基准换算 |
| BIOS 兼容表覆盖 | `W5` 用到的芯片组与代际组合在数据中可匹配 |
| 机箱参数口径 | 限长/限高取保守值，`notes` 注明口径（PRD 10.2 风险） |

**并行策略**：T1.1～T1.8 写入文件互不重叠（8 个独立文件），可并行；T1.9 必须在全部完成后串行执行。

## 七、风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| **R1** | 纯 JS 生成 `.xlsx` 可能不被某些软件识别 | 导出功能不可用 | 先写 `xlsx.js` 并用 **LibreOffice 实际打开验证**；若失败，降级为「导出 CSV（Excel 可直接打开）」并在界面标注，PRD M9-1 允许文本格式，需你确认降级 |
| **R2** | `file://` 下 `localStorage` 可能被浏览器限制或清空 | 配置/自定义数据丢失 | ① 存储不可用时明确提示；② 提供「导出/导入方案 JSON」做人工备份；③ 自定义数据与配置分开存储，降低互相影响 |
| **R3** | 机箱限长/限高厂商标注口径不一 | E5/E6/E7 判定偏差 | 取保守值；`notes` 注明口径；数值型字段在 `estimated[]` 标记（PRD 10.2） |
| **R4** | 数据整理耗时最长，且关键字段必须精确 | 拖慢整体进度 | 分品类并行；关键字段优先，非关键字段允许近似；CSV 机制保证你能自行修正 |
| **R5** | 插槽/板型字面量不统一 | E1/E4 大面积误判 | T0.1 的唯一枚举 + T1.9 专项交叉校验 |
| **R6** | 32 条规则组合可能漏报/误报 | 核心价值受损 | 每条 ≥1 正例 ≥1 反例；≥6 个整机场景回归（T2.9） |
| **R7** | 内联数据使产物变大 | 打开变慢 | 目标 < 1.5 MB；超限则压缩 JSON 键名或按品类懒解析 |

## 九、立即可执行的第一步

阶段 0 不依赖任何确认，可立刻开始：

```bash
# 在当前工作目录执行（Node 已随 DSH 提供）
NODE="node"

# T0.1 → T0.4 产出后验证
"$NODE" tools/gen-schema.mjs
"$NODE" tools/gen-csv-templates.mjs
"$NODE" tools/validate-data.mjs
```

产出：`src/core/enums.js`、`schema/fields.js`、`schema/hardware.schema.json`、`tools/*.mjs`、`csv-templates/*.csv`。

> **单一数据源原则（T0.2 的实现方式）**：`schema/fields.js` 是字段规范的**唯一**机器可读来源；`schema/hardware.schema.json` 由 `tools/gen-schema.mjs` 生成，`validate-data.mjs` 与 `gen-csv-templates.mjs` 都直接引用 `fields.js`。
> 这样避免了「JSON Schema 与实际校验逻辑不一致」这类问题，也省掉了手写通用 JSON Schema 校验器的成本（零依赖约束下）。
